## 一、部署架构

> **老板决策**：Docker Compose 单机部署，不使用 K8s。MVP 阶段单机足以承载预期流量，降低运维复杂度。

```
                    ┌──────────────┐
                    │   用户请求    │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │   CDN + DNS  │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │  Nginx 容器  │
                    │ (SSL终结/反代) │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │   API 容器   │
                    │  (单实例)    │
                    └──────┬───────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
  ┌──────▼──────┐  ┌───────▼──────┐  ┌──────▼──────┐
  │   MySQL     │  │    Redis     │  │  OSS 对象   │
  │   容器      │  │    容器      │  │  存储       │
  │  (单实例)   │  │ (256MB LRU)  │  │ (图片/文件) │
  └─────────────┘  └──────────────┘  └─────────────┘
                           │
                    ┌──────▼───────┐
                    │   外部服务   │
                    │ 推送 / AI 服务│
                    └──────────────┘
```

### 1.1 单机部署说明

Docker Compose 单机部署，所有服务运行在同一台 ECS 上：

- **Nginx 容器**：SSL 终结、反向代理、静态资源分发、限流。
- **API 容器**：Go 后端单实例（2 核 2G），承载 P0 阶段流量。
- **MySQL 容器**：单实例，数据卷持久化，每日全量备份到 OSS（详见第六章备份策略）。
- **Redis 容器**：单实例，256MB 内存上限 + LRU 淘汰策略。
- **OSS 对象存储**：图片/文件托管（外部服务，不在单机内）。
- **推送 / AI 服务**：调用外部 SaaS（极光推送、AI 行程规划），不在单机内。

**扩容路径**：当单机 QPS 超过 800 时横向扩展——可将 API 拆分为多实例 + Nginx 负载均衡，或迁移至多机部署；MySQL/Redis 视读写压力拆分独立实例。

## 三、Docker 容器化

### 3.1 后端 Dockerfile

```dockerfile
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

FROM alpine:3.19
RUN apk add --no-cache ca-certificates tzdata
ENV TZ=Asia/Shanghai
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]
```


## 四、Docker Compose 生产部署

> **老板决策**：Docker Compose 单机部署，不使用 K8s。MVP 阶段单机足以承载预期流量，降低运维复杂度。

### 4.1 生产环境 docker-compose.yml

```yaml
version: "3.8"

services:
  api:
    image: registry.xunlvji.com/api:v2.1.7
    restart: always
    ports:
      - "8080:8080"
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    environment:
      - DB_HOST=mysql
      - DB_PORT=3306
      - REDIS_HOST=redis
      - REDIS_PORT=6379
    deploy:
      resources:
        limits:
          cpus: "2"
          memory: 2G
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"

  mysql:
    image: mysql:8.0
    restart: always
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: xunlvji
    volumes:
      - mysql_data:/var/lib/mysql
      - ./mysql/conf.d:/etc/mysql/conf.d
      - ./mysql/backup:/backup
    deploy:
      resources:
        limits:
          cpus: "2"
          memory: 2G
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"

  redis:
    image: redis:7-alpine
    restart: always
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    volumes:
      - redis_data:/data
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 512M
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

  nginx:
    image: nginx:1.25-alpine
    restart: always
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d
      - ./nginx/certs:/etc/nginx/certs
      - ./nginx/logs:/var/log/nginx
    depends_on:
      - api
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 512M
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost/"]
      interval: 10s
      timeout: 5s
      retries: 5
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "5"

volumes:
  mysql_data:
  redis_data:
```

### 4.2 资源限制

| 服务 | CPU 限制 | 内存限制 | 实例数 | 说明 |
|------|----------|----------|--------|------|
| api | 2 核 | 2G | 1（单实例） | Go 后端，承载 P0 流量 |
| mysql | 不限制（共享宿主机） | 不限制（共享宿主机） | 1 | 单实例，数据卷持久化 |
| redis | 0.5 核 | 512M（maxmemory 256MB + LRU） | 1 | 缓存，256MB 上限 + LRU 淘汰 |
| nginx | 0.5 核 | 512M | 1 | SSL 终结、反代、限流 |

> 单机总配置建议：4 核 8G ECS，预留约 1 核 1G 给系统与监控。

### 4.3 扩容路径

- **触发条件**：当单机 QPS 持续超过 800，或 API 容器 CPU 使用率长期 > 80%。
- **第一步（P1 阶段）**：API 扩展为多实例（2-3 个），Nginx upstream 负载均衡。
- **第二步**：MySQL/Redis 拆分为独立 ECS，减轻单机压力。
- **第三步**：流量进一步增长时，评估迁移至多机 / K8s 集群方案。

## 五、CI/CD 流水线

### 5.1 GitHub Actions 流程

```
Push/PR → 代码检查 → 单元测试 → 构建镜像 → 推送镜像仓库 → SSH 部署到 ECS（Docker Compose）
```

### 5.2 流水线配置

```yaml
name: CI/CD
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.22"
      - run: go test ./... -cover

  build-and-deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build and Push Image
        run: |
          docker build -t registry.xunlvji.com/api:${{ github.sha }} .
          docker push registry.xunlvji.com/api:${{ github.sha }}
      - name: Deploy to ECS via SSH (Docker Compose)
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.ECS_HOST }}
          username: ${{ secrets.ECS_USER }}
          key: ${{ secrets.ECS_SSH_KEY }}
          script: |
            cd /opt/xunlvji
            docker compose pull api
            docker compose up -d api
            docker compose ps api
```

## 六、备份策略

| 数据 | 备份频率 | 保留时间 | 方式 |
|------|----------|----------|------|
| MySQL 全量 | 每天 02:00 | 30 天 | mysqldump + OSS |
| MySQL 增量 | 每 15 分钟 | 7 天 | binlog 备份 |
| Redis RDB | 每天 03:00 | 7 天 | 自动 RDB 快照 |

| 日志 | 每天 | 90 天 | ELK 归档 |

**灾难恢复 RTO**：4 小时内恢复服务
**灾难恢复 RPO**：最多丢失 30 分钟数据

## 八、发布流程

### 8.1 发布审批

```
开发自测 → 提交 PR → Code Review → 合并到 main → 自动部署到 staging
→ QA 验证 → 发布审批 → 部署到生产 → 线上验证 → 发布完成
```

### 8.2 灰度发布

```
10% 流量（观察 30 分钟）→ 50% 流量（观察 30 分钟）→ 100% 流量
```

### 8.3 回滚策略

```
发现问题 → 停止灰度 → 回滚旧镜像（docker compose up -d 旧 tag）→ 通知团队 → 复盘
```

回滚时间目标：**5 分钟内完成**

## 九、安全措施

| 措施 | 说明 |
|------|------|
| HTTPS 强制 | 所有 API 请求强制 HTTPS |
| 密钥管理 | 使用 .env 文件 + Docker secrets，不硬编码 |
| SQL 注入防护 | 参数化查询，ORM 防护 |
| XSS 防护 | 输入转义，CSP 头 |
| CSRF 防护 | Token 验证 |
| 限流 | Nginx 层限流（100 req/s） |
| DDoS 防护 | CDN + WAF 防护 |
| 数据加密 | 敏感数据 AES-256 加密存储 |
| 日志脱敏 | 手机号、密码等信息脱敏 |

## 十、运维手册

### 10.1 常用命令

```bash
# 查看容器状态
docker compose ps

# 查看日志
docker compose logs -f api

# 进入容器
docker compose exec api /bin/sh

# 回滚（拉取旧镜像并重启）
docker compose pull api && docker compose up -d api

# 重启服务
docker compose restart api

# 数据库备份
docker compose exec mysql mysqldump -u root -p xunlvji > backup_$(date +%Y%m%d).sql
```

### 10.2 应急预案

| 场景 | 处理步骤 |
|------|----------|
| 服务不可用 | 检查容器状态 → 检查日志 → 回滚旧镜像 → 如无法恢复，重启整组服务 |
| 数据库故障 | 检查 MySQL 容器状态 → 从最近备份恢复 → 通知运维 |
| 图片加载失败 | 检查 CDN 状态 → 切换备用 CDN → 检查 OSS |
| AI 服务异常 | 降级为本地规则排序 → 通知 AI 服务方 |
| 大流量冲击 | 开启 Nginx 限流 → 升级 ECS 配置 → P1 阶段扩展为多实例 |
