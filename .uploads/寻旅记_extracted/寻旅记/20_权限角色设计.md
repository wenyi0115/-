## 一、角色定义

### 1.1 用户角色体系

| 角色 | 角色编码 | 说明 | 权限范围 |
|------|----------|------|----------|
| 游客 | - | 未登录用户 | 只读浏览，不能发布/互动/打卡 |
| 普通用户 | user | 已登录 | 浏览、发布、互动、打卡、行程、社交 |
| 认证创作者 | creator | 认证通过 | 比普通用户多：曝光加权、粉丝置顶、参与分润 |
| 内容审核员 | reviewer | 内部角色 | UGC 内容审核、打标、违规处理 |
| 运营管理员 | operator | 内部角色 | 榜单管理、推荐内容、封禁账号 |
| 系统管理员 | admin | 超级管理员 | 全权限 |

> **说明**：角色编码与 `user` 表的 `role` 字段（VARCHAR(20)）对应。`role` 和 `user_role` 表支持一个用户拥有多个角色（如同时为 creator + reviewer），此时取权限并集。`user.role` 字段存储主角色，用于快速判断。

### 1.2 角色存储与管理

角色信息存储于以下数据库表（详见 `05_数据库设计文档.md`）：

| 表名 | 说明 |
|------|------|
| `user.role` | 用户主角色字段，取值：user / creator / reviewer / operator / admin，默认 user |
| `role` | 角色定义表，存储角色编码、名称、权限列表（JSON 格式） |
| `user_role` | 用户角色关联表，支持一个用户拥有多个角色 |
| `creator_application` | 创作者认证申请表，记录申请信息及审核状态 |

**角色分配规则**：
- 用户注册时，`user.role` 默认为 `user`，同时在 `user_role` 表中插入对应记录。
- 创作者认证通过后，`user.role` 更新为 `creator`，同时在 `user_role` 表中插入 creator 角色记录。
- 审核员、运营、管理员由上级角色直接任命，通过后台管理界面操作。
- 角色变更时，同步更新 `user.role`（主角色）和 `user_role`（全部角色）。
- 所有角色变更操作记录至 `audit_log` 表。

## 三、权限检查规则

### 3.1 访问控制层级

1. **路由层**：检查用户是否登录，对应角色是否有权限访问此路由
2. **控制器层**：检查当前操作是否有权限（例如只能修改自己内容）
3. **服务层**：最终数据权限检查，确认操作对象所有权
4. **数据库层**：查询时增加权限条件（只查询自己创建的）

### 3.2 数据权限规则

| 数据类型 | 访问规则 |
|----------|----------|
| 公开内容 | 所有人可读 |
| 用户创建内容 | 创建者可写，所有人可读 |
| 用户个人数据 | 仅自己可读/写 |
| 私信 | 仅收发双方可读 |
| 系统配置 | 仅管理员可读/写 |

### 3.3 用户认证认证流程

```
请求 → 检查 JWT Token → Token 有效 → 获取用户 ID 和角色 → 权限检查 → 允许/拒绝
                 ↓
              Token 无效 → 返回 2001 → 客户端跳转登录页
```

## 四、角色审核流程

### 4.1 创作者认证流程

1. 用户在个人中心提交申请（数据写入 `creator_application` 表）
   - 提供真实姓名（real_name）、身份证号（id_card）、作品集（portfolio）
   - 说明创作方向（美食/历史/自然风光等）
   - 申请状态（status）初始为 `pending`
2. 运营管理员审核（1-3 工作日）
   - 检查身份真实性
   - 检查过往内容质量
   - 通过 → 更新 `creator_application.status` 为 `approved`，`user.role` 更新为 `creator`，`user_role` 表插入 creator 角色记录
   - 不通过 → 更新 `creator_application.status` 为 `rejected`，填写 `review_note`，用户可修改后重新申请
3. 认证通过 → 给予流量加权，开启分润权限
4. 审核记录：`reviewer_id`、`reviewed_at`、`review_note` 字段记录审核信息

**身份证号加密存储方案**：

创作者认证涉及的身份证号（id_card）属于最高敏感等级个人信息，必须采用以下加密存储方案：

| 处理环节 | 方案 | 说明 |
|---------|------|------|
| 传输加密 | HTTPS/TLS 1.3 | 全程加密传输，禁止明文传输 |
| 存储加密 | AES-256-GCM | 使用 AES-256 对称加密存储加密后的身份证号，密钥托管于 KMS（密钥管理服务） |
| 展示脱敏 | 仅显示前 3 位 + 后 4 位 | 前端展示时脱敏为 `320***********1234` 格式 |
| 哈希校验 | SHA-256 哈希 | 仅存储身份证号的 SHA-256 哈希值用于重复校验（防止同一身份证重复认证），不存储明文 |
| 密钥轮换 | KMS 自动轮换 | 加密密钥每 90 天自动轮换，历史密钥保留用于解密旧数据 |
| 访问控制 | 仅管理员可查看 | 审核员、运营管理员均不可查看完整身份证号，仅管理员有权限 |

**数据库存储设计**：

```sql
-- creator_application 表
id_card_hash  VARCHAR(64)   -- SHA-256 哈希，用于唯一性校验
id_card_encrypted TEXT       -- AES-256-GCM 加密后的密文
id_card_masked  VARCHAR(20)  -- 脱敏展示：320***********1234

-- 加密密钥不在数据库中存储，统一由 KMS 管理
```

> **合规说明**：此方案符合《个人信息保护法》第二十八条（敏感个人信息处理规则）和《数据安全法》第二十一条（数据分类分级保护）要求。

### 4.2 内容审核员申请

- 由运营管理员直接任命，不开放用户申请

### 4.3 运营管理员申请

- 由系统管理员直接任命

### 4.4 审核员与运营角色职责边界

| 维度 | 审核员（reviewer） | 运营管理员（operator） |
|------|-------------------|----------------------|
| 核心职责 | 内容审核、违规处理 | 用户管理、内容运营、配置管理 |
| 内容审核 | 审核 UGC 内容（通过/驳回）、打标 | 查看审核记录，不可直接审核 |
| 用户管理 | 无权限 | 查询用户、封禁/解封用户 |
| CPS 管理 | 无权限 | 查看 CPS 订单、佣金结算 |
| 榜单管理 | 无权限 | 编辑热榜、推荐位 |
| 数据看板 | 无权限 | 查看运营数据看板 |
| 配置中心 | 无权限 | 热词管理、勋章配置、推送模板 |
| 举报处理 | 处理举报内容 | 查看举报记录、申诉处理 |
| 任命权限 | 无 | 任命/撤销审核员 |

> **关键原则**：审核员专注内容审核流水线，运营管理员管理平台运营与用户生态，两者权限互斥，不可兼任。管理员（admin）拥有全部权限，负责任命审核员和运营管理员。

### 4.5 封禁用户权限说明（统一口径）

> **封禁用户（`user.status = 0` 禁用）权限统一为「可登录、不可发布」**：
> - **可登录**：封禁用户可正常登录 App，浏览自己已发布的内容、行程、勋章、消息等，账号数据保留可见。
> - **不可发布**：封禁期间禁止发布新内容、打卡、评论、点赞、关注、私信、创建行程等写操作；触发时拦截并提示「账号已被封禁，如有异议请申诉」。
> - 此口径在 2.1 内容模块、4.4 用户管理及全项目统一；**封禁 ≠ 禁止登录**，仅限制写权限。解封后恢复正常权限。

## 六、隐私权限设置

> 隐私设置存储于 `user_setting` 表（详见 `05_数据库设计文档.md`），每个用户一条记录，注册时自动创建默认配置。

### 6.1 用户可配置隐私选项

| 选项 | 数据库字段 | 默认值 | 说明 |
|------|-----------|--------|------|
| 足迹可见性 | footprint_public | public（公开） | VARCHAR(16)，值 public（公开）/ friends（仅好友）/ private（仅自己） |
| 发布内容是否公开 | content_public | 1（公开） | 所有新发布内容默认可见性：0-否, 1-是 |
| 是否允许他人私信 | allow_dm_scope | all（所有人） | all / followers / nobody |
| 位置信息是否公开 | location_public | 0（不公开） | 是否在打卡中公开精确位置，默认不公开精确位置，仅展示城市级别 |
| 历史行程是否公开 | history_public | 0（不公开） | 是否允许他人查看你的历史行程：0-不公开, 1-公开 |
| 收藏列表是否对外可见 | show_favorites | 0（不公开） | 是否允许他人查看你的收藏列表：0-不公开, 1-公开 |
| 关注/粉丝列表是否对外可见 | show_following | 0（不公开） | 是否允许他人查看你的关注/粉丝列表：0-不公开, 1-公开 |
| 个人主页可见性 | profile_visibility | public（公开） | VARCHAR(16)，值 public（公开）/ friends（仅好友）/ private（仅自己） |
| 个性化推荐开关 | personalized_recomm | 1（开启） | 是否启用个性化推荐：0-关闭, 1-开启 |

### 6.2 隐私保护强制规则

1. 用户手机号永远不对第三方公开
2. 打卡位置只存经纬度不存具体地址（除非用户主动公开）
3. 第三方登录只获取昵称和头像，不获取通讯录/位置等敏感信息
4. 注销账号时 30 天冷静期后彻底删除所有用户数据
5. 用户可以导出所有自己的个人数据
