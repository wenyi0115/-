## 一、设计原则

### 1.1 核心原则

| 原则 | 说明 |
|------|------|
| **不阻塞原则** | 空状态和可恢复错误不应阻塞用户使用其他功能。底部导航栏始终可用，用户可随时切换到其他Tab。 |
| **引导优先原则** | 空状态不仅是"告知无内容"，更是引导用户完成下一步操作的入口。每个空状态必须包含一个明确的行动引导。 |
| **一致性原则** | 所有空状态使用统一的视觉语言（图标尺寸、文案风格、按钮样式），确保用户在不同页面获得一致的体验。 |
| **透明化原则** | 网络异常、加载失败等错误状态必须明确告知用户发生了什么，并提供可操作的恢复路径，不做技术黑盒。 |
| **离线友好原则** | 行程执行场景（打卡）支持离线操作，其他场景在无网络时给出明确提示但保留已缓存内容的浏览能力。 |

### 1.2 状态分类

```
页面状态
├── 加载中（Loading）
│   ├── 首次加载（骨架屏 / 全屏Loading）
│   └── 刷新加载（下拉刷新指示器 / 局部Loading）
├── 空状态（Empty）
│   ├── 初始空状态（用户从未产生数据）
│   └── 操作后空状态（筛选/搜索后无结果）
├── 正常状态（Normal）
│   └── 内容展示
├── 错误状态（Error）
│   ├── 网络异常（无网络 / 服务器不可达）
│   ├── 服务器错误（500 / 503）
│   ├── 业务错误（参数错误 / 权限不足）
│   └── 操作失败（上传失败 / 提交失败）
└── 边界状态（Edge）
    ├── 网络切换（WiFi ↔ 移动网络）
    └── 离线模式（打卡场景）
```

### 1.3 标准横幅高度规范

全局统一黄色横幅（提示/警告类）高度标准：

| 横幅类型 | 高度 | 适用场景 | 示例 |
|---------|------|---------|------|
| 紧凑型 | 36pt | 单行文字提示，无按钮 | 下拉刷新失败提示、登录页无网络提示 |
| 标准型 | 48pt | 单行文字 + 右侧操作按钮 | WiFi切换到移动网络提示 |
| 含按钮型 | 56pt | 文字 + 多个操作按钮 | GPS定位失败（含"开启定位""手动选择城市"按钮） |

> **通用规则**：横幅背景色为黄色 #FFF8E1，文字 13pt~14pt，紧贴内容区顶部显示，不阻塞内容浏览。

## 二、通用空状态组件

### 2.1 组件规范

通用空状态组件 `EmptyStateView` 作为全局可复用组件，所有页面空状态均基于此组件配置。

```
┌──────────────────────────────────────┐
│                                      │
│                                      │
│           ┌─────────────┐            │
│           │             │            │
│           │   空状态图标  │            │
│           │  (120×120pt) │            │
│           │             │            │
│           └─────────────┘            │
│                                      │
│           主标题文案（17pt，深色）       │
│                                      │
│       副标题文案（14pt，灰色，最多两行）    │
│                                      │
│       ┌─────────────────────┐        │
│       │   操作按钮（主色填充）   │        │
│       └─────────────────────┘        │
│                                      │
│       次要操作（灰色文字，14pt）         │
│                                      │
└──────────────────────────────────────┘
```

### 2.2 视觉规范

| 属性 | 规范 |
|------|------|
| 组件位置 | 页面内容区域垂直居中，距离顶部导航栏下方 |
| 图标尺寸 | 120pt × 120pt（iOS @2x: 240px, @3x: 360px） |
| 图标风格 | 线性插画风格，使用主色 #4EC3F7 的 20% 透明度版本，线条粗细 2pt |
| 主标题 | 字号 17pt，字重 Medium，颜色 #1A1A1A，单行，图标下方间距 16pt |
| 副标题 | 字号 14pt，字重 Regular，颜色 #999999，最多两行，行高 1.5，主标题下方间距 12pt |
| 操作按钮 | 高度 44pt，圆角 22pt，主色 #4EC3F7 填充，白色文字 15pt Medium，水平内边距 32pt，按钮上方间距 24pt |
| 次要操作 | 字号 14pt，颜色 #666666，按钮下方间距 16pt，带下划线 |
| 底部留白 | 组件底部保留至少 40pt，避免与底部导航栏重叠 |

### 2.3 图标库

| 图标名称 | 使用场景 | SVG描述 |
|---------|---------|--------|
| `empty-box` | 通用空内容（无数据） | 开口的盒子，内部飘出几缕轻烟 |
| `empty-search` | 搜索无结果 | 放大镜图标，右侧带问号气泡 |
| `empty-collection` | 收藏为空 | 空心五角星，周围散落几颗小星 |
| `empty-publish` | 发布为空 | 羽毛笔，笔尖悬停在空白纸面上方 |
| `empty-trip` | 行程为空 | 地图标记，标记点处为问号 |
| `empty-message` | 消息为空 | 空白的对话气泡，内部无文字 |
| `empty-follow` | 关注为空 | 人物剪影，右侧带加号 |
| `empty-nearby` | 附近无内容 | 指南针，指针微微偏离正北方向 |
| `empty-network` | 网络异常 | 地球图标，信号波纹断裂 |
| `empty-upload-fail` | 上传失败 | 向上的箭头，箭头处带叉号 |
| `empty-location` | GPS定位失败 | 定位标记，中心点闪烁问号 |

### 2.4 动效规范

| 动效 | 描述 |
|------|------|
| 图标入场 | 从下方 20pt 处淡入+上移，duration 400ms，easing: ease-out |
| 按钮入场 | 图标入场后延迟 200ms 启动，scale 0.9 → 1.0 + opacity 0 → 1，duration 300ms |
| 文字入场 | 与图标同步，opacity 0 → 1，duration 300ms |

| 属性 | 规范 |

### 12.4 离线打卡同步冲突

**场景ID**：`CHECKIN_SYNC_CONFLICT`

> 离线打卡联网同步时可能遇到多种冲突场景，详见 06_API接口文档.md「4.7 离线打卡同步 - 冲突处理策略」。

| 冲突类型 | 触发条件 | 展示方式 | 是否阻塞 | 恢复路径 |
|---------|---------|---------|---------|---------|
| 重复打卡冲突 | 同一点位在线已打卡，离线又打卡（多设备） | 弹窗："该点位已打卡，离线记录未同步" + "查看已有打卡"按钮 | 否 | 点击"查看已有打卡"跳转至该点位打卡记录；离线记录保留本地 7 天后自动清理 |
| 点位已删除 | 离线打卡时点位已从行程移除 | 弹窗："该点位已从行程中移除，打卡记录已保存为草稿" + "转为主动发布"按钮 | 否 | 点击"转为主动发布"进入发布页，预填离线打卡内容 |
| 行程已结束 | 离线打卡时行程已完成或删除 | 弹窗："行程已结束，打卡记录已保存为草稿" + "转为主动发布"按钮 | 否 | 同上，转为主动发布内容 |
| GPS 未验证 | 到店打卡 GPS 偏差 > 100 米 | Toast："打卡已同步（GPS 未验证）"（3 秒） | 否 | 打卡记录正常展示，但 `gps_verified` 标记为 `false`，卡片上不显示 GPS 验证标识 |
| 重复打卡去重 | 离线打卡与在线打卡间隔 < 5 分钟 | 无提示（静默去重） | 否 | 系统自动保留时间更早的记录，用户无感知 |

**设计原则**：数据不丢失。任何无法同步的离线打卡记录均保留在本地草稿箱，提供"转为主动发布"的降级路径，确保用户离线打卡内容不会因冲突而消失。

### 12.5 打卡弹窗表单校验失败

## 十五-7、账号禁言中提示

### 15.7.1 禁言状态操作拦截

**场景ID**：`ACCOUNT_MUTED`

当用户处于禁言状态（因违规处置被禁言 7 天 / 30 天 / 永久禁言，详见 04_运营与合规手册 1.7.4 违规处置标准）时，发布 / 评论 / 私信 / 打卡等需要发言权限的操作将被拦截。

| 维度 | 内容 |
|------|------|
| 触发条件 | 用户处于禁言状态时，点击发布 / 评论 / 私信 / 打卡等需要发言权限的操作 |
| 展示方式 | Toast 提示（错误样式，3 秒） |
| Toast文案 | "您的账号已被禁言，预计 YYYY-MM-DD 解禁"（永久禁言时提示"您的账号已被永久禁言，如有疑问请联系客服"） |
| 是否阻塞 | 是。禁言期间不可执行发布 / 评论 / 私信 / 打卡等发言类操作；浏览、收藏、搜索等非发言类操作不受影响 |
| 用户操作 | 等待禁言期满自动解禁；或通过「申诉」入口提交申诉（见 04_运营与合规手册 1.7.4） |
| 解禁恢复 | 禁言期满后自动恢复发言权限，无需用户操作；永久禁言需通过申诉流程由运营复核 |

> **提示文案规则**：Toast 中"预计 XX 解禁"的 XX 为禁言到期日期（格式 YYYY-MM-DD），由服务端根据禁言时长计算后下发；永久禁言时不展示解禁日期，仅提示联系客服。
