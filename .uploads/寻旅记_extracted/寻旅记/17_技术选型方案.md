## 四、数据层

### 4.1 数据库

| 组件 | 选型 | 版本 | 说明 |
|------|------|------|------|
| 主数据库 | MySQL | 8.0+ | 空间索引、JSON 字段、窗口函数 |
| 缓存 | Redis | 7.0+ | 热点数据、会话、排行榜、分布式锁 |
| 搜索引擎 | Elasticsearch | 8.x | 全文搜索、模糊搜索、地理位置搜索（**MVP 阶段不部署自建 ES，改用 MySQL FULLTEXT，详见 4.3**） |
| 消息队列 | Redis Streams | 7.0+ | MVP 阶段异步通知、数据同步、日志收集（复用 Redis，降低运维成本；后续流量增大可迁移至 Kafka） |

> **MVP 搜索选型警示**：4 核 8G 单机同时承载 Go + MySQL + Redis，若再叠加自建 Elasticsearch（默认堆内存即占用 2G+，索引膨胀后更易 OOM），单机内存必然不足，存在高频 OOM 风险。因此 MVP 阶段**明确不部署自建 ES 集群**，搜索能力降级到 MySQL FULLTEXT，详见 4.3。

### 4.2 缓存策略

| 数据 | 过期时间 | 说明 |
|------|----------|------|
| 热门地点 | 1 小时 | 高频读 |
| 热门路线 | 30 分钟 | 中频读 |
| 行程排序结果 | 1 小时 | AI 排序结果缓存，命中率 70%+，省 70% 调用 |
| 用户 Token | 2 小时 | Access Token 短期有效，配合 Refresh Token 续期 |
| 验证码 | 5 分钟 | 防重复 |
| 搜索结果 | 5 分钟 | 减少搜索后端压力（MVP 阶段为 MySQL，规模期为 ES） |
| 排行榜 | 1 小时 | 定时刷新 |

### 4.3 MVP 搜索降级方案（P0-11）

> **背景**：4 核 8G 单机跑 Go + MySQL + Redis 已接近内存上限，自建 ES 集群会触发 OOM；当前 4.1 规划的 ES 集群仅作为规模期目标架构，MVP 阶段必须降级。

**MVP 阶段方案：MySQL FULLTEXT 全文检索替代 ES**

| 阶段 | 搜索方案 | 适用 DAU | 说明 |
|------|----------|----------|------|
| MVP | MySQL 8.0 FULLTEXT 索引（`ngram` 分词） | 0-1 万 | 不部署 ES，零额外内存/运维成本，单机即可承载 |
| 增长期 | 火山引擎 ES Serverless 托管版 | 1 万-10 万 | 托管免运维、按量付费，无需自建集群 |
| 规模期 | 火山引擎 ES Serverless（扩容）/ 自建 ES 集群 | 10 万+ | 按需扩容，DAU 过万后迁移 |

**MVP 实施要点**：
1. **建索引**：对 `place.name`、`place.description`、`route.title`、`guide.title` 等高频检索字段建立 `FULLTEXT` 索引，分词器使用 `WITH PARSER ngram`（兼容中文，token 长度默认 2）。
   ```sql
   ALTER TABLE place ADD FULLTEXT INDEX ft_name_desc (name, description) WITH PARSER ngram;
   ALTER TABLE route ADD FULLTEXT INDEX ft_title (title) WITH PARSER ngram;
   ```
2. **查询方式**：使用 `MATCH(name, description) AGAINST('关键词' IN BOOLEAN MODE)`，配合 `LIMIT` 分页与 Redis 搜索结果缓存（5 分钟）。
3. **能力边界**：MySQL FULLTEXT 可满足 MVP 的关键词检索、模糊匹配；复杂的聚合统计、地理位置打分排序等高级能力在迁移到 ES 后再启用，MVP 阶段用 `ORDER BY` + 业务排序兜底。
4. **迁移路径**：业务层封装统一 `SearchService` 接口（`Search(keyword, filters, page)`），MVP 实现为 MySQL，规模期切换为 ES 实现并双写校验后切流，上层业务无感知。

**结论**：MVP 阶段不部署任何自建 ES 集群，搜索由 MySQL FULLTEXT 承载；DAU 过万（增长期）后再迁移到火山引擎 ES Serverless 托管版，避免单机 OOM 风险，同时降低运维与硬件成本。

### 4.4 火山引擎降级方案（P1-11）

> **背景**：当前 AI（豆包）、内容安全、对象存储（TOS）、CDN 全部依赖火山引擎，存在单云单厂商锁定风险。任一服务故障将导致核心功能（AI 行程、内容审核、图片加载）不可用。本节定义各核心依赖的自动降级方案，确保火山引擎局部故障时业务连续。

**降级总原则**：
- 所有外部依赖统一封装为 `Provider` 接口（如 `AIProvider`、`ContentSafetyProvider`、`StorageProvider`、`CDNProvider`），主备实现可热切换。
- 健康检查：每 30 秒探活，连续 3 次失败（或错误率 > 30%）触发自动降级；恢复后自动回切主链路。
- 降级与回切均记录审计日志，运营可在管理后台手动强制指定主/备链路。

#### 4.4.1 AI 服务降级（豆包 → 通义千问）

| 链路 | 提供方 | 模型 | 用途 | 切换条件 |
|------|--------|------|------|----------|
| 主链路 | 火山引擎 | 豆包 Pro / Lite | 行程排序、AI 对话、攻略生成、图片识别 | 默认 |
| 备链路 | 阿里云 | 通义千问 Plus | 同上（能力对齐） | 豆包 API 连续超时/5xx 错误率 > 30%，或区域级故障 |

**实施要点**：
- 业务层封装统一 `AIProvider.Generate(prompt, params)`，主实现调豆包，备实现调通义千问（参见 2.3.2 模型对比）。
- 降级期间关闭「攻略预生成」离线任务，仅保障实时 AI 行程规划/对话，降低备链路成本冲击。
- 降级期间对用户透明，仅在前端 AI 内容仍标注"AI 生成"；备链路费用较高，恢复后优先回切豆包。
- 提示词（Prompt）模板需在豆包/通义千问双端调优验证，避免降级后输出质量骤降。

#### 4.4.2 内容安全降级（火山引擎内容安全 → 阿里云内容安全）

| 链路 | 提供方 | 能力 | 切换条件 |
|------|--------|------|----------|
| 主链路 | 火山引擎内容安全 | 图片+文字审核（涉黄/涉暴/涉政/广告/违禁品） | 默认 |
| 备链路 | 阿里云内容安全 | 同上（图片+文字审核） | 火山引擎内容安全 API 不可用或错误率 > 30% |

**实施要点**：
- 封装统一 `ContentSafetyProvider.CheckText/CheckImage`，主备实现可切换。
- 降级期间审核标准不变（见 04_运营与合规手册 1.7 内容审核标准），仅切换底层服务商。
- **极端兜底**：主备均不可用时，UGC 内容降级为「先发布后审」（仅自己可见→AI/人工审核通过后公开），避免正常内容被阻断；恢复后对降级期间内容批量补审。

#### 4.4.3 对象存储降级（TOS → 阿里云 OSS）

| 链路 | 提供方 | 用途 | 切换条件 |
|------|--------|------|----------|
| 主链路 | 火山引擎 TOS | UGC 图片/封面存储 | 默认 |
| 备链路 | 阿里云 OSS | 同上 | TOS 上传/读取连续失败或区域故障 |

**实施要点**：
- 封装统一 `StorageProvider.Upload/GetURL`，上传链路主备可切换。
- **已有数据不迁移**：降级仅对新上传内容写入 OSS；读取时按 URL 前缀路由（TOS 域名走 TOS、OSS 域名走 OSS），存量 TOS 数据仍从 TOS 读取。
- CDN 回源配置需同时支持 TOS 与 OSS 两个源站（见 4.4.4）。
- 双方均使用 WebP 压缩 + 图片处理参数兼容（TOS/OSS 均支持缩略图/裁剪/水印）。

#### 4.4.4 CDN 降级（火山引擎 CDN → 阿里云 CDN）

| 链路 | 提供方 | 用途 | 切换条件 |
|------|--------|------|----------|
| 主链路 | 火山引擎 CDN | 全国图片/静态资源加速 | 默认 |
| 备链路 | 阿里云 CDN | 同上 | 火山引擎 CDN 回源异常或大面积节点故障 |

**实施要点**：
- 域名 `static.xunlvji.com` 同时接入火山引擎 CDN 与阿里云 CDN（双 CDN 配置），通过 DNS 智能解析切换。
- 回源支持多源站：火山引擎 CDN 回源 TOS，阿里云 CDN 回源 OSS（与 4.4.3 联动）。
- 降级通过 DNS TTL 短时间（60 秒）切换，配合健康检查自动化；切换期间缓存命中率短暂下降属预期。
- 切换不影响已缓存的旧 URL 访问，仅影响新建连接的解析路径。

#### 4.4.5 降级矩阵速查

| 故障场景 | 影响功能 | 自动降级动作 | 用户感知 |
|----------|----------|--------------|----------|
| 豆包 API 故障 | AI 行程规划/对话/攻略生成 | 切换通义千问；暂停攻略预生成 | 无（响应可能略慢） |
| 火山引擎内容安全故障 | UGC 审核 | 切换阿里云内容安全；主备均挂则「先发布后审」 | 无（审核仍正常）/ 内容延迟公开 |
| TOS 故障 | 图片上传 | 新图改写 OSS；存量仍读 TOS | 无 |
| 火山引擎 CDN 故障 | 图片/静态资源加载 | DNS 切换阿里云 CDN | 短暂加载变慢 |
| 火山引擎整体区域故障 | 全部上述功能 | AI→通义、审核→阿里云、存储→OSS、CDN→阿里云 CDN 全量切换 | 无/轻微降速 |

- 阿里云作为备选，仅在追求极致稳定性时考虑；腾讯云与阿里云价格相近但 AI 能力较弱，不推荐。

## 七、技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| MySQL 性能瓶颈 | 读多写少，QPS 超 5000 | 读写分离 + Redis 缓存 + 分表 |
| 图片存储成本 | UGC 增长快，存储量大 | WebP 压缩 + CDN + 冷热分层 |
| AI 服务成本 | 每调用成本高 | 缓存常见结果 + 离线预生成 + 分级调用 |
| 地图 SDK 依赖 | 高德商业授权费用及政策变化 | 高德定位 SDK 免费；预留商业授权预算（500 元/月）；保留百度地图 SDK 备选方案 |
| 微信小程序审核 | 审核周期长 | 提前提交，预留缓冲时间 |
| CPS 联盟资质 | 携程联盟、美团联盟均需企业资质 | P0 早期先用饿了么（个人可申请）+ 高德打车 CPS，企业资质就绪后接入携程（P1）与美团（P1） |
| 火山引擎单云依赖 | AI/内容安全/存储/CDN 全依赖火山引擎，单厂商故障致核心功能不可用 | 主备双链路自动降级：AI→通义千问、内容安全→阿里云内容安全、存储→阿里云 OSS、CDN→阿里云 CDN，见 4.4 |

## 八、性能分析

### 8.1 架构瓶颈分析

| 模块 | 风险等级 | 瓶颈点 | 对策 |
|------|----------|--------|------|
| 图片加载 | 高 | UGC 图片量大、首屏加载慢 | CDN 加速 + WebP 压缩 + 懒加载 |
| 数据库 | 中 | 高并发读写、慢查询 | Redis 缓存 + 索引优化 + 读写分离 |
| AI API | 中 | 调用延迟、成本 | 结果缓存 + 分级调用 + 攻略预生成 |
| 搜索 | 低 | ES 单点压力 | MVP 用 MySQL FULLTEXT（无 ES 单点问题）；规模期用火山引擎 ES Serverless 托管版（免自建运维），见 4.3 |

### 8.2 Go 语言高并发优势

- 同等配置下，Go 的并发处理能力是 Java 的 2-3 倍。
- 协程（goroutine）轻量，单机可支撑数十万并发连接，内存占用低。
- 部署简单（单二进制），运维成本低，适合初创团队。
- **结论**：撑到 50 万日活无需大改架构。

- **AI 辅助开发**：前端页面生成、后端接口开发、测试用例编写等重复性工作由 AI 承担，进一步压缩固定成本。

- **冷启动零预算**：暂不投入 KOL 付费推广，通过 AI 生成内容 + 老板校园资源种子用户自然增长。
