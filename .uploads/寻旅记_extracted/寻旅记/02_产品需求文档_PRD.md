# 寻旅记 · 产品需求文档（PRD）

> 版本：v2.0.3 | 日期：2026年6月 | 状态：正式版 | 用途：产品、开发、测试团队执行标准
> 平台：P0 - 微信小程序；P1 - iOS App / Android App

---

## 一、产品概述

### 1.1 产品定位

寻旅记是一款**旅行垂直内容社区**。通过结构化攻略（AI 整理+爬取+人工校准）、真实 UGC 打卡记录、可执行路线与 AI 智能规划，解决现有平台种草强执行弱、内容碎片化、信息不结构化的痛点。核心定位是内容社区而非工具——用户在这里发现、记录、分享旅行内容，内容越积越多形成壁垒。

### 1.2 核心价值主张

**对国内用户**：不用在多个 App 间跳转，浏览打卡地→一键加入行程→AI 自动排序→出发→逐点打卡→一键导航/打车。路线自带交通、消费预估，打卡可跳过。

**对创作者**：结构化发布模板降低创作门槛，顺手发布打卡内容，内容越积越多，后来者参考。社交互动（评论、点赞、"有用"投票）让优质内容获得长期曝光。

**平台壁垒**：结构化攻略（AI 整理+爬取+持续更新）比小红书零散笔记更专业；真实打卡数据（评分/人均消费/去过人数）比大众点评更有社区感。**核心壁垒：别人有内容但没有真实到访数据，你有。** 打卡内容带 GPS 验证标记和实际消费记录，是时间积累型壁垒，无法被快速复制。

### 1.3 目标用户

- **国内自由行游客（18-35 岁）**：周末城市漫步、短途周边游、长假长途旅行。核心诉求是找灵感 → 做决策 → 规划路线 → 实地打卡 → 记录分享。
- **旅行内容创作者**：喜欢拍照、乐于分享的旅行爱好者。核心诉求是低门槛发布、获得互动反馈、未来获得收益。
- **普通浏览者**：漫无目的地刷内容。核心诉求是被种草、收藏灵感。
- **入境外国游客（长期战略愿景）**：现阶段不显示入境游功能，但数据结构完整预留（multi_lang/foreigner_info/target_audience 字段），国内 MVP 跑通后视条件上线。详见 4.3 入境游预留策略。

### 1.4 竞品差异化

| 竞品 | 优势 | 短板 | 寻旅记的差异 |
|------|------|------|-------------|
| 小红书 | 内容种草 | 无工具，种草与执行割裂；笔记零散，无结构化信息 | 种草直达执行 + 结构化数据 |
| 抖音 | 流量传播 | 碎片化，无结构化内容 | 结构化路线 + 深度内容 |
| 大众点评 | 评分/消费数据 | 无社区，无社交，无旅行专属内容 | 社区+真实打卡+社交互动 |
| 携程 | 交易闭环 | 无社区，用完即走 | 社区+内容壁垒 |
| 马蜂窝 | 攻略丰富 | 无执行，行程落地难 | 可执行路线+一键打卡 |

> 注：竞品分析选取 5 家主要竞品，涵盖内容种草、流量传播、消费数据、交易闭环、攻略社区等维度，与方案书保持一致。

## 二、产品原则

1. **内容优先**：首页是内容流，不是工具按钮。用户先被内容吸引，再使用工具。
2. **结构化数据**：所有攻略、打卡地、路线都用结构化模板展示，拒绝长文划不到底。
3. **一键转化**：任何内容详情页都保留"加入行程"入口（位于底部"功能"按钮内，路线详情为"使用此路线"），用户浏览→加入→AI 排序→出发，无需手动编辑。
4. **AI 辅助透明**：AI 整理的内容明确标注，把"仅供参考"转化为"邀请实地验证"的行动钩子。AI 用于内容整理和行程规划，不做假 UGC。
5. **真实 UGC 壁垒**：用户打卡时顺手发布内容，内容越积越多，形成其他平台没有的真实数据壁垒。
6. **社交驱动**：评论点赞、评论回复、避雷"有用"投票、关注/取消关注，构建社区互动闭环。
7. **简化操作**：行程构建只需"加入"和"出发"，AI 自动估算距离/耗时/消费，自动排序最优路线。

## 三、数据模型

### 3.1 核心实体

**用户（User）**
- 账号、昵称、头像、信用分（简化版 MVP）、偏好标签、去过城市数
- 粉丝数、关注数、获赞数

**地点（Place）**——客观存在的 POI 基础数据
- 名称、分类（吃喝/玩乐/逛看/户外/逛街/住宿，共 6 大分类）
- 坐标（经纬度）、地址、营业时间、电话
- 人均消费、封面图、推荐等级（必去/可去/避雷）
- 建议时长、标签
- `extra_fields` JSON——存专属模板数据（按 category 动态结构，如吃喝存菜系/招牌菜、住宿存房型/设施）
- `cps_links` JSON——存 CPS 分销链接（按平台聚合，如携程门票/酒店、饿了么吃喝、高德打车）
- `multi_lang` JSON——多语言预留字段（结构化字段的多语言版本，预留入境游，现阶段留空）
- `foreigner_info` JSON——外国游客信息预留字段（外文标识/外文讲解/支付方式等，现阶段留空不展示）
- `target_audience`——目标受众标记（domestic/inbound/outbound，现阶段只做 domestic）
- `region` VARCHAR(20)——省份/州代码，用于入境游区域筛选

**打卡记录（Check-in Record）= UGC 内容**——打卡与发布共用一张表，是用户对地点的真实反馈
- 关联用户、关联地点
- 图片、评分、感受描述、实际消费（`actual_cost`）
- 避雷建议、打卡时间
- 可见性（公开/仅自己可见）
- `source`——内容来源（trip_checkin 行程中打卡 / manual_publish 主动发布）
- `extra_data` JSON——打卡专属内容（按 place 的 category 动态结构，如餐厅打卡存菜品评价、景点打卡存拍照机位）
- `content_richness`——内容丰富度分级（light 轻量 / standard 标准 / rich 丰富），系统根据填写完整度自动计算，控制展示卡片大小与排序权重
- `gps_verified`——GPS 验证标记（布尔，打卡时定位在打卡点 100 米范围内记为 true）
- `region` VARCHAR(20)——省份/州代码，用于入境游区域筛选

> 设计说明：打卡即发布，行程中打卡和主动发布产出同一种东西——打卡地页面的一条内容。区别仅在真实度与丰富度，用 `source` 区分来源、`content_richness` 控制展示。详见 3.4 内容来源机制。

**路线（Route）**——用户或 AI 创建的结构化行程模板
- 标题、封面图、总时长、总预算
- 点位列表（有序，含时间、停留时长、消费、交通方式）
- 适合人群、分类（半日游/一日游/两日游/三日及以上）
- 标签、创作者信息、来源标签（用户/AI/官方）
- 使用人数、收藏数、评分

**攻略（Guide）**——运营侧发布的内容，用户不可发布
- 标题、封面图、分类（自然生态/历史文化/人工娱乐/城市公共/交通枢纽/红色旅游/宗教场所，共 7 大分类）
- 城市、时长、价格、阅读时长
- 内容正文、必看亮点、避雷提醒
- 实用信息（地址、开放时间、交通方式）
- AI 验证人数、来源标签（固定为"AI"）

**行程（Trip）**——用户个人规划的、可执行的行程单
- 名称、日期、状态（待出发/进行中/已完成）
- 点位列表（有序，含每个点位的打卡状态）
- 关联的路线（可选）
- 进度统计（已打卡数/总点数/已跳过数）

**评论（Comment）**——楼中楼结构
- 关联目标（路线/打卡地/攻略）
- 发布者、内容、时间
- 一级评论 + 二级回复（关联父评论）
- 点赞数（like_count）

### 3.2 实体关系

```
用户 ──→ 打卡记录（一对多）
用户 ──→ 路线（一对多，创作者）
用户 ──→ 行程（一对多）
用户 ──→ 评论（一对多）
地点 ──→ 打卡记录（一对多）
路线 ──→ 行程（一对多，使用此路线生成）
路线 ──→ 地点（多对多，点位关联）
行程 ──→ 地点（多对多，点位关联）
```

### 3.3 打卡地类型模板

打卡地按 6 大分类管理，每类采用"通用模板（必填）+ 专属模板（可选）"的双层结构。一碗牛肉面和一个 5A 景区不再共用同一套字段，信息密度按类型匹配。

#### 6 大分类

| 分类 | 典型场景 | 是否 MVP 专属模板 |
|------|----------|------------------|
| 吃喝 | 餐厅、小吃店、咖啡馆、茶馆 | 是 |
| 住宿 | 酒店、民宿、客栈 | 否（后期） |
| 户外 | 山岳、徒步路线、露营地 | 否（后期） |
| 玩乐 | 主题乐园、水上乐园、演出 | 是 |
| 逛看 | 博物馆、古迹、展览、景区 | 是 |
| 逛街 | 商圈、步行街、市集 | 否（后期） |

> MVP 阶段先做吃喝、逛看、玩乐 3 类高频类型的专属模板，其余 3 类只填通用模板即可。

#### 通用模板（所有类型必填）

所有打卡地共用的 8 个通用必填字段，AI 爬取时必须填充，用户发布时也需填写：

| 字段 | 说明 | 示例 |
|------|------|------|
| 地点名称 | 打卡地名称 | 黄鹤楼 |
| 图片 | 打卡地封面图/实景图（至少 1 张） | — |
| 描述 | 打卡地简介与特色说明 | 江南三大名楼之一 |
| 人均消费 | 门票或人均消费金额 | 免费 / ¥80 / 人均¥35 |
| 建议时长 | 推荐停留时间 | 1-2 小时 |
| 避雷建议 | 需要注意的避坑提示 | 节假日人多，建议错峰 |
| 定位 | 经纬度坐标 + 地址（高德 POI 自动回填） | — |
| 分类 | 打卡地分类（吃喝/玩乐/逛看/户外/逛街/住宿） | 逛看 |

> 以下运营信息字段由系统自动获取，非用户填写：

| 字段 | 说明 | 示例 |
|------|------|------|
| 预约状态 | 是否需要预约及预约渠道 | 需预约（公众号）/ 免预约 |
| 实时开放状态 | 当前是否营业 | 营业中 / 已闭馆 |
| 最佳游览时段 | 一天中最佳到访时间 | 上午 9-11 点（人少） |
| 厕所位置 | 卫生间方位提示 | 入口右侧 50 米 |
| 网络信号 | 室内/山区信号情况 | 移动良好、电信较差 |
| 无障碍信息 | 是否有无障碍设施 | 有无障碍通道、无电梯 |

#### 专属模板（可选，按分类动态展示）

用户选择分类后，系统自动展示该分类的专属字段，可跳过不填。专属字段存入 Place 的 `extra_fields` JSON、打卡内容存入 CheckInRecord 的 `extra_data` JSON，应用层按 category 做校验和渲染。

| 分类 | 专属字段 | 用户场景示例 |
|------|----------|-------------|
| 吃喝 | 菜系、招牌菜品（图+名+价）、口味标签、是否排队、排队时长 | "这家鱼糕店的招牌荆州鱼糕必点，人均35，中午要排队20分钟" |
| 住宿 | 房型、价格区间、设施、入住/退房时间、是否含早 | "标准间288/晚，停车免费，含早餐，14:00入住" |
| 户外 | 难度等级、海拔、路线长度、最佳季节、安全提示、装备建议 | "登山路线中等难度，3km，建议春秋前往，需穿防滑鞋" |
| 玩乐 | 适合人群、游玩时长、排队情况、是否需预约、刺激程度 | "方特适合亲子，建议玩一整天，周末排队1小时" |
| 逛看 | 展览类型、是否需预约、免费/收费、参观路线建议、拍照提示 | "博物馆常设展免费，建议参观2小时，二楼有越王勾践剑" |
| 逛街 | 商圈类型、停车信息、营业特色、最佳时段、品牌列表 | "户部巷小吃街，建议晚上去，停车在对面商场，人均50吃饱" |

> 核心原则：AI 爬取的字段必须是用户做决策时真正需要的，无关字段缩减或移除。

### 3.4 内容来源机制

#### 核心理念：打卡即发布

打卡和发布不是两个动作，是同一个动作的两种触发方式。行程中打卡和主动发布产出同一种东西——打卡地页面的一条内容（CheckInRecord）。区别只在真实度与丰富度。

```
发布 = 写内容，地点是引用的，人不一定去过
打卡 = 人到了现场，反馈是真实的，地点是行程里已有的
```

#### 两条内容来源，互不冲突

| 来源 | 触发 | 动作 | 特点 | 价值 |
|------|------|------|------|------|
| 行程中打卡（量） | 用户在行程中到达点位 | 拍照+评分+可选一句话 | 快、顺手、真实 | 积累真实数据 |
| 主动发布（质） | 用户不在行程中主动分享 | 填通用模板+可选专属模板 | 详细、有深度 | 优质内容吸引新用户 |

两者共用一张表（CheckInRecord），用 `source` 字段区分来源（trip_checkin / manual_publish），用 `content_richness` 控制展示权重。

#### content_richness 分级与卡片展示

系统根据用户填写完整度自动计算内容丰富度，对应不同卡片规格：

| 分级 | 填写内容 | 卡片规格 | 展示优先级 |
|------|----------|----------|-----------|
| 轻量（light） | 照片 + 评分 | 小卡片 | 默认 |
| 标准（standard） | 照片 + 评分 + 文字 | 中卡片 | 提升 |
| 丰富（rich） | 照片 + 评分 + 文字 + 专属模板 | 大卡片 | 优先推荐 |

> 简单打卡也有价值：一张照片证明"地方长这样"、一个评分证明"有人给了4.5分"、一个时间戳证明"2026年6月还有人去过"、一句"鱼糕不错"帮后来者决策、实际消费¥35比攻略写的更准。大众点评很多评价也就一句话+一张图，照样撑起百亿平台。

#### 打卡地详情页展示逻辑

```
打卡地详情页
  ├── 基础信息（名称/地址/营业时间/人均/评分/通用模板字段）
  ├── 真实数据聚合（自动计算）
  │     ├── 综合评分 = 所有打卡评分的均值
  │     ├── 人均消费 = 所有打卡实际消费的均值
  │     ├── 去过人数 = 打卡记录总数
  │     └── 最新照片墙 = 所有打卡照片（瀑布流）
  ├── 打卡记录列表（混合展示）
  │     ├── 丰富的打卡 → 大卡片
  │     ├── 标准的打卡 → 中卡片
  │     └── 轻量的打卡 → 小卡片
  └── 优质内容置顶（主动发布的长内容）
```

#### 排序逻辑

打卡地页面内容排序：**打卡内容（source=trip_checkin）> 发布内容（source=manual_publish）**，真实到过的永远排在前面。同一来源内按 content_richness（丰富 > 标准 > 轻量）和时间倒序排列。

#### 产品核心壁垒

**别人有内容但没有真实到访数据，你有。** 打卡内容可能很简单，但"人真的去了、真的花了钱、真的拍了照"，真实性满分。发布内容可能很详细，但"听说的、查的、网上看的"，真实性打折。真实到访数据是时间积累型壁垒，无法被快速复制。

## 四、全局架构

### 4.1 平台矩阵

| 平台 | 定位 | 功能范围 |
|------|------|---------|
| iOS App | 主阵地 | 全功能 |
| Android App | 国内商店上架 | 功能同 iOS |
| 微信小程序 | 轻量入口，辅助推广引流 | 浏览、收藏、简单行程规划、分享裂变 |

### 4.2 账号体系

- 手机号登录（国内）
- Apple ID / Google / Email 登录（海外）
- 微信一键登录（小程序）
- 游客模式：未登录用户可浏览内容，点击"跳过"即视为同意《用户协议》和《隐私政策》，收藏/发布/评论/关注/创建行程等操作触发登录拦截
- 收藏、行程、足迹、消息在 App 与小程序间实时同步（草稿箱为第三阶段功能）

### 4.3 入境游预留策略

**现阶段不显示入境游相关功能，但数据结构完整预留。** 国内 MVP 跑通后再视情况开启。

**预留内容**：
- Place 表的 `multi_lang` JSON 字段：结构化字段的多语言版本，现阶段留空
- Place 表的 `foreigner_info` JSON 字段：外国游客信息（外文标识/外文讲解/支付方式），现阶段留空不展示
- Place 表的 `target_audience` 字段：目标受众标记（domestic/inbound/outbound），**现阶段只做 domestic**
- AI 爬取攻略/打卡地时顺手记录外文标识、外文讲解、支付方式 3 个字段，成本极低，存入 `foreigner_info` 但不展示

**语言包预留**：
- 语言包支持中文（简体/繁体）、English、日本語、한국어、Français、Español、Deutsch
- 首页左上角保留"中/EN"语言切换入口，现阶段切换仅影响 UI 文案，不切换内容源
- 结构化字段双语展示、UGC 长文本翻译、评论实时翻译等功能在入境游上线后启用

**上线触发条件（四项需同时满足）**：

### 4.4 定位状态机

接入**高德定位 SDK（免费）**，提供定位、POI 搜索、逆地理编码（坐标反查地址）能力。

| 模式 | 触发条件 | 首页展示 | 导航/打车 |
|------|---------|---------|----------|
| 计划模式 | 用户未开启 GPS，手动选择城市 | 入境指南、热门城市、准备清单 | 灰色显示"落地后启用" |
| 旅行模式 | 用户开启 GPS 实时定位（中国境内） | 附近推荐、正在打卡 | 完全可用 |
| 手动模式 | 用户拒绝 GPS 授权后的降级模式 | 该城市内容 | 可用（以该城市为起点） |

> **三种模式边界说明**：
> - **计划模式**：用户未开启 GPS，手动选择城市，附近以城市中心计算距离。
> - **旅行模式**：用户开启 GPS 实时定位，附近以实际位置计算距离。
> - **手动模式**：用户拒绝 GPS 授权后的降级模式，使用计划模式逻辑（手动选城市 + 城市中心距离）。

定位权限首次打开询问，拒绝后进入手动模式（降级为计划模式逻辑），**不强制定位，拒绝定位仍可手动选城市使用**。

**三种场景的定位使用**：

| 场景 | 定位方式 | 说明 |
|------|----------|------|
| 发布打卡地定位 | 搜索选择（高德 POI 搜索，主选）+ 地图选点（备选） | 用户发布内容时通过搜索选择 POI，系统自动回填坐标和地址；搜索不到时可在地图上手动选点 |
| 行程中打卡定位 | 自动 GPS 定位 + 反查地址 | 用户点击"打卡"时自动获取当前 GPS 坐标，通过逆地理编码反查地址，与点位地址比对 |
| 打卡 GPS 验证 | 100 米范围判定 | GPS 定位在打卡点 100 米范围内时，通知栏弹出"你已到达 XX，点击打卡"；打卡记录带 `gps_verified` 标记（true/false） |

> GPS 验证失败不影响打卡，仅作为快捷入口和真实性标记。支持离线打卡：无网络时本地记录时间戳，联网后自动同步。

### 5.3.1 路线→行程转换规则

路线是别人分享的模板，行程是用户自己的旅行。用户浏览路线后可以一键将路线转化为可执行的行程。

#### 1. 转换触发

用户在路线详情页点击底部操作栏的"功能"按钮 → 弹出底部操作面板 → 选择"使用此路线" → 再次弹出选择面板，提供两个选项：

| 选项 | 说明 | 后续行为 |
|------|------|---------|
| 创建新行程 | 基于该路线创建一个全新的行程 | 弹出日期选择器 → 确认后跳转至新创建的行程详情页 |
| 加入已有行程 | 将该路线的点位追加到已有行程中 | 弹出已有行程列表（仅显示"待出发"和"进行中"状态的行程）→ 选择后 AI 自动合并排序 |

#### 2. 数据结构转换

路线（Route）转化为行程（Trip）时，字段映射关系如下：

| Route 字段 | Trip 字段 | 转换规则 |
|-----------|-----------|---------|
| `route_points`（含 `day_number`） | `trip_points` | 按顺序保留，`day_number` 不变 |
| `title` | `title` | 直接复制，用户可修改 |
| `cover` | `cover` | 直接复制，用户可修改 |
| `total_budget` | `budget` | 保留为参考值，用户可修改 |
| `total_duration` | `estimated_duration` | 保留为参考值，不可修改 |
| — | `start_date` | 用户选择出发日期 |
| — | `end_date` | 自动计算（start_date + estimated_duration - 1） |
| — | `visibility` | 默认"仅自己"（private），用户可主动选择公开（已确认：行程默认 private） |
| — | `source_route_id` | 关联原路线 ID，用于追溯和统计"使用此路线"次数 |

#### 3. AI 智能调整

路线转化为行程后，系统自动调用 AI 进行以下优化：

| 优化项 | 说明 | 示例 |
|--------|------|------|
| 开放时间校验 | 根据用户选择的出发日期，校验每个点位当天的营业/开放状态 | 周一出发 → 博物馆闭馆 → 自动提示"该点位周一闭馆，建议调整日期或跳过" |
| 游览顺序优化 | 根据点位间距离，重新计算最优游览顺序 | 原始路线 A→B→C，AI 发现 B→A→C 更高效 → 自动调整并标注变更 |
| 交通耗时估算 | 估算每日点对点交通耗时，填充 `trip_points` 的交通字段 | "A→B 驾车约 15 分钟、步行约 8 分钟" |
| 费用估算 | 基于人均消费和交通方式，估算每日和总费用 | 门票 ¥80 + 午餐 ¥50 + 打车 ¥25 = 日预算 ¥155 |
| 预算超支提醒 | 总费用超过路线原预算时弹窗提示 | "预估总费用 ¥1,200，路线预算 ¥1,000，超支 ¥200，建议调整" |

> AI 调整结果以"建议"形式展示，用户可逐项确认或回退。校验失败的提示出现在对应点位卡片上，以黄色警告样式展示。

#### 4. 转换后状态

- Trip 状态初始为 `pending`（待出发）
- 用户可从行程列表（底部导航"出发"Tab → 待出发）进入详情页进一步编辑
- 行程详情页支持：修改点位顺序、删除点位、添加新点位、调整预算、修改可见性
- 用户点击"开始行程"后，Trip 状态变更为 `active`（进行中），此时点位顺序锁定，仅支持跳过和打卡

### 5.4.1 打卡审核状态机

所有用户发布的打卡内容（CheckInRecord）在对外展示前需经过审核流程。系统采用"AI 初筛 + 信用分免审 + 人工复审"三级审核机制。

#### 1. 审核流程

用户发布打卡 → 系统自动审核（AI 初筛，5 秒内） → 信用分 ≥ 90 免人工审核直接发布 → 信用分 < 90 进入人工审核队列。

状态流转图：

```
用户提交打卡
    ↓
pending_review（待审核，用户可见"审核中"占位）
    ↓
ai_reviewing（AI 审核中，火山引擎内容审核 API 调用，<5 秒）
    ↓
    ├── ai_approved（AI 审核通过）
    │       ↓
    │       ├── 信用分 ≥ 90 → approved（直接发布，跳过人工审核）
    │       └── 信用分 < 90 → human_review（进入人工审核队列）
    │
    └── ai_rejected（AI 判定违规）
            ↓
        human_review（自动进入人工复审，不直接驳回）
            ↓
            ├── approved（人工判定通过，发布）
            └── rejected（人工判定违规，驳回）
```

#### 2. 各状态说明

| 状态 | 含义 | 用户可见性 | 操作 |
|------|------|-----------|------|
| `pending_review` | 用户提交后立即进入 | 用户在"我的发布"中看到"审核中"占位卡片 | 用户可删除，不可编辑 |
| `ai_reviewing` | 火山引擎内容审核 API 调用中 | 同 `pending_review`，用户无感知 | 系统自动流转，< 5 秒 |
| `ai_approved` | AI 审核通过 | 内容可见但标注"AI 已审核"标签 | 进入下一步判断（信用分路径） |
| `ai_rejected` | AI 判定违规 | 用户不可见 | 自动进入 `human_review` 人工复审 |
| `human_review` | 信用分 < 90 或 AI 驳回，进入人工队列 | 用户看到"审核中"占位 | 运营后台审核 |
| `approved` | 审核通过，完全公开可见 | 全平台可见，出现在首页信息流和打卡地详情页 | 可被点赞、评论、收藏 |
| `rejected` | 驳回 | 用户收到站内通知 + 驳回原因 | 用户可修改后重新提交，原内容保留为草稿 |

#### 3. 信用分免审规则

- 信用分 ≥ 90 的用户，AI 审核通过后直接进入 `approved` 状态，跳过 `human_review` 人工审核
- 信用分 < 90 的用户，AI 审核通过后仍需进入 `human_review` 人工审核
- 信用分 < 60 的用户，禁止发布新内容（返回错误码 `3007`，仅可浏览）
- 新用户（发布数 < 3）前 3 条内容强制人工审核，不受信用分免审规则影响

#### 4. 违规处罚

| 违规次数 | 处罚 | 说明 |
|---------|------|------|
| 第 1 次 | 信用分 -20，内容驳回 | 站内通知 + 驳回原因，可修改后重新提交 |
| 第 2 次 | 信用分 -20（累计 -40），警告通知 | 同上，附警告提示"累计 2 次违规，再有一次将禁言 7 天" |
| 第 3 次 | 信用分 -20（累计 -60），禁言 7 天 | 禁止发布和评论，仅可浏览，7 天后自动解除 |
| 第 4 次 | 信用分 -20（累计 -80），禁言 30 天 | 禁止发布和评论，仅可浏览，30 天后自动解除 |
| 第 5 次 | 永久禁言，信用分清零 | 需联系客服申诉解封 |

> 违规内容类型包括：涉政涉黄涉暴、虚假信息、广告引流、抄袭搬运、恶意避雷。AI 审核覆盖前 3 类，人工复审覆盖全部类型。

#### 5. 审核时效

| 审核环节 | 时效要求 | 超时处理 |
|---------|---------|---------|
| AI 审核（ai_reviewing） | < 5 秒 | 超时自动降级为 `human_review` |
| 人工审核（human_review） | < 2 小时（工作时间 9:00-22:00） | 超时自动通过，进入 `approved` |
| 夜间审核（21:00-次日 9:00） | 次日 11:00 前完成 | 次日 11:00 未处理自动通过 |

> 人工审核超时自动通过的机制是为了保障用户体验，避免内容长时间处于"审核中"状态。系统会记录超时通过的内容，供后续抽查。

### 5.5 攻略详情页

- AI 验证横幅：浅背景加主色边框，显示验证人数和"去打卡验证"按钮
- 必看亮点：横向滚动卡片
- 分类专属内容模块（每个分类展示用户真正需要的信息，AI 整理+爬取+人工校准+持续更新）：
  - **自然生态**（景区/公园/山岳）：最佳季节/时段、难度标识（轻松/中等/挑战）、交通到达（最近高铁站+路线+耗时）、门票信息（票价+预约渠道+优惠）、装备建议、景区内经典路线（大门→A→B→C→出口）、必看点位（3-5个）、餐饮补给、避雷提醒

  - **交通枢纽**（机场/高铁站/客运站）：到达方式（大巴/地铁/打车耗时+费用）、换乘指南、行李寄存（位置+价格+营业时间）、实用设施（母婴室/充电桩/ATM/SIM卡）、餐饮推荐
  - **人工娱乐**（主题乐园/水上乐园/演出）：必玩项目 Top3（刺激等级+排队预估+适合人群）、高效游玩路线（进门先冲哪个）、演出时间表、快速通道指南、园区餐饮推荐/避雷
  - **城市公共**（公园/广场/步行街）：开放区域、特色亮点（喷泉/雕塑/历史建筑）、周边配套（商场/餐厅/咖啡馆）、活动日历（近期市集/演出/展览）、无障碍设施

- 问大家：平铺式问答，支持提问、回答、点赞，底部提问输入框
- 底部固定栏：**喜欢(点赞) + 收藏 + 功能按钮 + 评论**；分享已移至顶部右上角。功能按钮点击展开操作面板，首项为"加入行程"（主操作），其余为导航、举报等

### 5.6 行程页

从底部导航"出发"进入。行程通过"浏览打卡地/攻略 → 点击加入行程 → AI 自动排序 → 出发"构建，用户无需手动编辑。

**页面结构**：
- 顶部导航：标题"我的行程"、右侧"编辑"文字按钮
- 状态 Tab：待出发、进行中、已完成，下划线主色

**行程卡片**：
| 状态 | 头部 | 主体 | 底部按钮 |
|------|------|------|---------|
| 进行中 | 深色背景（#1A1A2E）+名称+"进行中"珊瑚红(#FF6B6B)标签 | 进度条、计数、时间、日期 | 继续打卡（主）、查看详情（次）、分享（文字） |

| 已完成 | 浅灰背景+名称+"已完成"青绿标签 | 点位数量、日期范围 | 查看回顾（主）、分享行程（文字） |

- 底部操作栏：手动新建行程（描边）、AI 帮我规划（主色填充）

**简化的行程构建流程**：
1. 用户在首页/详情页浏览打卡地或攻略
2. 点击"加入行程" → 弹出已有行程列表或新建行程
3. AI 自动根据距离、开放时间、交通方式，为行程中的点位排序最优顺序
4. AI 自动估算：点对点距离 → 耗时、分类 → 建议停留时长、人均消费 → 预算
5. 用户确认/微调即可出发

**路线 vs 行程的关系**：

| 维度 | 路线（Route） | 行程（Trip） |
|------|--------------|-------------|
| 是什么 | 别人分享的模板 | 我自己的旅行 |
| 来源 | 用户发布/AI 生成/官方整理 | 路线转化/手动创建 |
| 内容 | 点位序列+推荐信息 | 点位+打卡+清单+账单+地图 |
| 复杂度 | 轻量，只展示信息 | 重量级，有工具功能 |
| 数量 | 无数条 | 一个人就几条 |

**路线详情页保持轻量，不加工具功能**（不做清单/账单/地图等），只展示信息。行程详情页才有工具功能。路线本身就是"复制"的替代品，用户要重复使用行程走"路线→创建行程"路径即可，**不做行程复制功能**。

**行程页不做项清单**：不做相册（打卡照片替代）、不做便签（打卡描述替代）、不做协作/多人、不做拖拽排序（AI 自动排序是卖点）、不做多选编辑、不做行程复制。

## 六、核心逻辑与规则

### 6.1 打卡机制

**打卡即发布**：用户到达点位后，点击"打卡"按钮 → 弹出打卡弹窗 → 上传图片（选填感受、消费、评分（1-5星）、避雷）→ 点击"打卡完成" → 关闭弹窗 → Toast"打卡成功" → 行程进度更新 → 点位变为已打卡状态 → **公开打卡自动发布为打卡地页面的一条内容（CheckInRecord，source=trip_checkin）**。

系统根据用户填写完整度自动计算 `content_richness`：仅照片+评分为轻量、加文字为标准、加专属模板为丰富。用户可在打卡后点击"展开更多"补充专属模板字段，提升内容丰富度。

GPS 辅助验证：GPS 定位在打卡点 100 米范围内时，通知栏弹出"你已到达 XX，点击打卡"。打卡记录带 `gps_verified` 标记（100 米内为 true）。GPS 验证失败不影响打卡，仅作为快捷入口和真实性标记。支持离线打卡：无网络时本地记录时间戳，联网后自动同步。

### 6.2 信用分体系（MVP 简化版）

初始分 100 分。

**加分项**：发布内容 +5、完成打卡 +5、被点赞 +1、被收藏 +2、被使用 +3、信息准确 +5、举报属实 +5。

**扣分项**：内容违规 -20、不实信息 -10、抄袭 -30、恶意避雷 -15。

**等级划分**（与 04/06/21 统一）：
- ≥90 分：优质创作者（免审 + 流量加权）
- 80-89 分：快速过审（30 分钟内完成审核）
- 70-79 分：普通创作者（抽审）
- 60-69 分：限制发布（强制审核）
- 低于 60 分：禁止发布（仅可浏览）

### 6.3 内容审核流程

**AI 预审**：发布后 5 秒内识别敏感词、违规图片、虚假信息。

**人工复审**：新用户前 3 条内容强制人工审核。信用分 ≥ 90 免审直接发布；80-89 快速过审（30 分钟内）；70-79 抽审；60-69 强制审核进入人工队列。信用分 < 60 禁止发布（返回错误码 `3007`）。

**发布状态**：审核中（仅自己可见）、已通过（公开）、已驳回（通知原因可修改重提）。

### 6.4 推荐算法排序因子

**个性化推荐为算法驱动，不调 AI API**——算法按用户行为画像调整内容比例，基于用户历史浏览、收藏、行程、打卡记录计算偏好，实时调整首页各 Tab 的内容配比。

- 用户状态权重：计划模式推送热门城市内容，旅行模式推送附近内容
- 内容质量分：近期验证 > 高评分 > 高收藏 > 高使用次数 > 新发布
- 内容时效性：30 天内权重最高，超过 180 天降权并提示
- 个性化标签：基于用户历史浏览、收藏、行程推荐
- 社交关系：关注创作者的新内容优先
- 真实度加权：带 GPS 验证的打卡内容权重高于普通发布内容

### 6.5 定位与地图规则

- 定位 SDK：接入高德定位 SDK（免费），提供定位、POI 搜索、逆地理编码能力
- 定位权限：首次打开询问，拒绝后进入计划模式，拒绝定位仍可手动选城市使用
- 距离计算：旅行模式用用户坐标到目标坐标；计划模式用城市中心坐标到目标坐标
- 发布打卡地定位：搜索选择（高德 POI 搜索，主选）+ 地图选点（备选）
- 行程中打卡定位：自动 GPS 定位 + 逆地理编码反查地址
- 打卡 GPS 验证：100 米范围内弹通知提示打卡，打卡记录带 `gps_verified` 标记
- 导航唤起：国内使用高德或百度 URL Scheme；海外使用 Google 或 Apple Maps
- 打车唤起：仅在中国境内可用，直接拼高德打车 URL Scheme（详见 6.8 CPS 分销机制）
- 计划模式下导航和打车按钮灰色显示"落地后启用"

### 6.6 离线机制

- 离线行程可下载到本地，包含所有点位信息、地址、开放时间、电话、导航链接（文本可离线查看，链接需联网唤起）
- 离线打卡：无网络时本地记录时间戳，联网后自动同步

### 6.7 AI 深化（6 个环节）

AI 贯穿用户旅行全链路的 6 个环节，分阶段落地。

| 环节 | 功能 | 实现阶段 |
|------|------|----------|
| 出发前 | AI 对话式规划行程 | 第二阶段（P1） |
| 浏览时 | 个性化推荐 | 第一阶段 |
| 行程中 | 实时调整 | 第一阶段（预算提醒）/ 第二阶段（天气/排队） |
| 打卡时 | AI 辅助填写 | 第二阶段 |
| 攻略内容 | AI 深度结构化 | 第一阶段（基础）/ 持续迭代 |
| 行程结束 | AI 生成回顾报告 | 第二阶段 |

**6 个环节详细说明**：

1. **出发前 — AI 对话式规划行程**：用户说需求（如"带娃去武汉玩两天，预算2000"）→ AI 生成完整行程（点位序列+时间+交通+预算）→ 用户确认/调整。替代手动规划，降低行程构建门槛。

2. **浏览时 — 个性化推荐**：算法按用户行为画像调整内容比例（不调 AI API），基于用户历史浏览、收藏、行程、打卡记录计算偏好，实时调整首页各 Tab 的内容配比。详见 6.4。

3. **行程中 — 实时调整**：
   - 跳过重排：用户跳过点位后，AI 自动重新计算剩余路线最优顺序
   - 天气感知调整：根据实时天气推荐室内/室外点位（第二阶段）
   - 排队/超时提示：提示当前点位排队情况，建议跳过或调整（第二阶段）
   - 预算超支提醒：行程账单总花费接近/超过预算时提醒（第一阶段）

4. **打卡时 — AI 辅助填写**：用户上传图片后，AI 识别自动填充菜品名称/地点名称/评分建议/描述文案，用户确认或修改后提交，降低打卡填写门槛（第二阶段）。

5. **攻略内容 — AI 深度结构化**：跨源对比（多平台信息交叉验证）、实时校验（营业时间/价格/开放状态）、智能摘要（长文提炼关键信息）、个性化展示（按用户偏好调整信息优先级）。AI 整理的内容明确标注，把"仅供参考"转化为"邀请实地验证"的行动钩子。

6. **行程结束 — AI 生成回顾报告**：行程总结（走过的点位/总时长/总消费）、亮点提取（AI 挑选最佳照片和时刻）、照片智能整理（按点位/时间分组）、行程海报（一键生成可分享的图文海报）、分享文案（AI 生成适合社交平台的文案）（第二阶段）。

**分阶段落地**：
- **第一阶段**：个性化推荐 + 预算超支提醒（AI 对话式规划行程推至 P1）
- **第二阶段**：天气感知调整 + 排队/超时提示 + AI 辅助打卡 + AI 回顾报告

### 6.8 CPS 分销机制

通过 CPS 分销链接实现初步收益，**系统自动匹配，用户不参与挂载**。

> **老板决策（v2.0.3）**：P0 阶段只接高德打车 + 饿了么；携程 + 美团推至 P1。

**合作平台**：

| 平台 | 覆盖品类 | 对接方式 |
|------|----------|----------|
| 携程联盟 | 门票、酒店 | 联盟 API 搜索匹配 |
| 饿了么联盟 | 吃喝（餐饮外卖） | 联盟 API 搜索匹配 |
| 高德打车 | 交通（打车） | 直接拼高德打车 URL，不需要搜索 |
| 美团 | 到店团购（吃喝/玩乐） | 联盟 API 搜索匹配 |

**匹配流程**：

```
Place 创建/更新时
  ↓ 按 category 调对应平台 API 搜索
  ↓ 匹配规则过滤（名称相似度+坐标距离+POI ID 比对）
  ↓ 生成 CPS 链接
  ↓ 存入 Place 的 cps_links JSON
  ↓ 每日定时刷新（链接有效期/价格变动）
  ↓ 匹配不到 → 不显示对应按钮
```

**分类与平台映射**：

| 打卡地分类 | 对接平台 |
|-----------|----------|
| 吃喝 | 饿了么联盟 |
| 住宿 | 携程联盟（酒店） |
| 玩乐/逛看 | 携程联盟（门票） |
| 逛街/户外 | 暂无对接（后期美团） |
| 交通（行程内） | 高德打车 |

> 攻略详情页 CPS 映射：自然生态/历史文化/人工娱乐/红色旅游/宗教场所 → 携程联盟（门票）；城市公共/交通枢纽 → 暂无对接。

**分类选错兜底**：AI 推荐分类（基于高德 POI type 映射）→ 匹配失败不显示 CPS 按钮 → 后台人工修正分类后重新匹配。

**展示位置**：
- 攻略详情页：实用信息区展示对应平台 CPS 按钮（订门票/订酒店/点外卖）
- 打卡地详情页：营业信息区展示对应平台 CPS 按钮
- 行程详情页点位卡片：点位卡片展示对应平台 CPS 按钮
- 行程交通：点位间交通展示高德打车按钮

> CPS 分销为第一阶段核心收益来源，系统自动匹配分销链接。详见第十章产品阶段重划。

### 6.8.1 CPS 分销落地细节

#### 1. CPS 平台对接清单

各平台通过联盟 API 对接，获取返佣链接。对接所需资质（营业执照 + ICP 备案）已具备。

| 平台 | 覆盖品类 | 对接方式 | 返佣结算周期 | 状态 |
|------|----------|----------|-------------|------|
| 携程联盟 | 门票、酒店预订 | API 对接，获取返佣链接 | T+30 | 第二阶段（P1）对接 |
| 美团联盟 | 餐饮外卖、到店团购 | API 对接，获取返佣链接 | T+15 | 第二阶段（P1）对接 |
| 饿了么联盟 | 外卖配送 | API 对接，获取返佣链接 | T+15 | 第一阶段（P0）对接 |
| 高德打车 | 出行打车 | API 对接，获取返佣链接 | T+7 | 第一阶段（P0）对接 |

> 各平台返佣比例由平台侧决定，寻旅记不参与定价。返佣收入在结算周期后由平台统一结算至寻旅记企业账户。

#### 2. CPS 展示位置

CPS 入口根据页面类型和打卡地分类，在以下位置展示对应平台按钮：

> **P0 阶段仅展示饿了么 + 高德打车入口，携程/美团按钮在 P1 阶段启用。** 下表为完整规划，P0 阶段携程/美团相关按钮位置预留但不下发数据。

| 页面 | 展示位置 | 展示规则 |
|------|---------|---------|
| 打卡地详情页 | 营业信息区 | 餐饮类 → 美团/饿了么按钮；景区/玩乐类 → 携程门票按钮；住宿类 → 携程酒店按钮；其他分类无匹配 → 不展示 |
| 攻略详情页 | 实用信息区 | 自然生态/历史文化/人工娱乐/红色旅游/宗教场所 → 携程门票按钮；城市公共/交通枢纽 → 暂无对接，不展示 |
| 路线详情页 | 每个点位卡片下方 | 按点位分类展示对应 CPS 入口（同打卡地详情页规则） |
| 行程详情页 | 行程进行中时，每个点位卡片下方 | 按点位分类展示对应 CPS 入口，完成后消失 |

CPS 按钮样式统一为：主色边框 + 平台图标 + 平台名称 + 动作文案（如"订门票""订酒店""点外卖""打车"），按钮宽度自适应，高度 36pt，圆角 8pt。

#### 3. CPS 链接生成规则

用户点击 CPS 按钮后，后端执行以下流程生成跳转链接并记录：

```
用户点击 CPS 按钮
    ↓
后端生成带追踪参数的跳转链接
  参数：uid（用户 ID）+ place_id（地点 ID）+ platform（平台标识）+ timestamp（时间戳）
    ↓
用户跳转至平台完成交易
    ↓
平台回调通知订单完成
    ↓
后端记录 cps_order 表
  字段：order_id、uid、place_id、platform、amount、commission、status、created_at、settled_at
    ↓
到达结算周期后平台统一结算
```

**cps_order 表核心字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `order_id` | VARCHAR(64) | 平台订单号，唯一 |
| `uid` | BIGINT | 触发用户 ID |
| `place_id` | BIGINT | 关联地点 ID |
| `platform` | VARCHAR(20) | 平台标识（ctrip/meituan/eleme/amap） |
| `amount` | DECIMAL(10,2) | 订单金额 |
| `commission` | DECIMAL(10,2) | 预估返佣金额 |
| `status` | VARCHAR(20) | 订单状态（pending/paid/settled/refunded） |
| `created_at` | DATETIME | 订单创建时间 |
| `settled_at` | DATETIME | 结算时间 |

#### 4. CPS 合规标注

根据《中华人民共和国广告法》和《互联网广告管理办法》要求，所有 CPS 入口必须进行合规标注：

| 标注要求 | 具体做法 |
|---------|---------|
| 广告标识 | 所有 CPS 入口标注"推广"字样（灰色 10pt，符合《广告法》第十四条）；瀑布流中 CPS 内容占比 ≤ 20% |
| 可识别性 | "广告"标识与按钮内容有明显区分（颜色、字号不同），确保消费者能够辨明其为广告 |
| 平台来源 | 按钮文案明确标注平台名称（如"携程订门票""美团点外卖"），不模糊平台来源 |
| 免责声明 | 详情页底部统一展示免责文案："以上服务由第三方平台提供，寻旅记仅提供信息展示，交易及售后由对应平台负责" |

> 合规风险提示：CPS 推广属于互联网广告范畴，需确保广告标识显著、不误导用户。若未来上线信息流广告，需额外申请《互联网广告发布登记》。

#### 5. 后端预留位置

对于暂时无法对接的平台（如部分小众 OTA、境外平台），后端 `cps_links` 字段预留 JSON 结构，前端统一渲染逻辑，未来接入新平台时无需改动前端代码。

**cps_links 字段 JSON 结构**：

```json
{
  "ctrip_ticket": {
    "enabled": true,
    "url": "https://...",
    "label": "携程订门票",
    "price": 80.00
  },
  "ctrip_hotel": {
    "enabled": false,
    "url": null,
    "label": "携程订酒店",
    "price": null
  },
  "meituan_food": {
    "enabled": true,
    "url": "https://...",
    "label": "美团点外卖",
    "price": null
  },
  "eleme": {
    "enabled": false,
    "url": null,
    "label": "饿了么外卖",
    "price": null
  },
  "amap_taxi": {
    "enabled": true,
    "url": "amapuri://...",
    "label": "高德打车",
    "price": null
  }
}
```

**前端渲染逻辑**：遍历 `cps_links` 对象，`enabled=true` 且 `url` 非空的条目渲染对应 CPS 按钮。`enabled=false` 或 `url` 为空的条目不渲染。新增平台接入时，只需在 `cps_links` 中新增 key-value 对，前端无需改动。

- 核心服务可用性 ≥ 99.9%
- 第三方服务故障降级方案：翻译失败显示原文，AI 规划降级为规则引擎推荐
- 实时监控接口响应时间、错误率、用户崩溃率

## 十、产品阶段重划

产品按四个阶段推进，每阶段有明确目标与核心指标。**第一阶段已启动 CPS 分销（系统自动匹配），第二阶段深化变现。**

### 10.1 四个阶段总览

| 阶段 | 目标 | 核心收益方式 | 核心指标 |
|------|------|-------------|----------|
| 第一阶段 | 跑通核心闭环 | CPS 分销 | 日活 / 留存 / 打卡数 |
| 第二阶段 | 增长+初步收益 | CPS 深化+广告 | 月活 / CPS 收入 / UGC 量 |
| 第三阶段 | 生态+规模收益 | 商户/广告/创作者 | 商户数 / 广告收入 |
| 第四阶段 | 国际化 | 入境游 | 海外用户量 |

### 10.2 第一阶段：跑通核心闭环

**核心链路**：刷内容 → 加入行程 → 出发 → 打卡 → 发布。

**第一阶段保留功能**：
- 专属模板（3 类：吃喝、逛看、玩乐）
- 搜索功能
- 热门城市（首发 3 城）
- 个性化推荐（算法驱动）
- 预算超支提醒
- 行程账单总预算展示（明细推至 P1）

**第一阶段砍掉/延后功能**：
- 榜单（延后）
- 足迹地图（延后）
- 勋章系统（移至 P1 优先级，第一阶段不做）
- AI 助手对话/对话式规划行程（#106 推至 P1）
- 账单明细分类统计/手动补录（P0 仅保留总预算展示）
- 天气感知调整、排队/超时提示、AI 辅助打卡、AI 回顾报告（移至第二阶段）

**核心指标**：日活（DAU）、7 日留存、每周新增真实打卡数。

### 10.3 第二阶段：增长+初步收益

**核心目标**：用户增长 + CPS 深化+广告变现。

**新增功能**：
- AI 助手对话/对话式规划行程（从 P0 推至 P1）
- 账单明细分类统计/手动补录
- 天气感知调整
- 排队/超时提示
- AI 辅助打卡
- AI 回顾报告
- 勋章系统
- 足迹地图
- 榜单

**核心指标**：月活（MAU）、CPS 收入、UGC 量（内容发布量）。

### 10.4 第三阶段：生态+规模收益

**核心目标**：构建商户生态 + 广告 + 创作者体系。

**新增功能**：
